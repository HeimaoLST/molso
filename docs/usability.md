# 用户与 agent 使用体验审查

本轮沿着安装、首次调用、录入、选择消费方式、调用失败后的恢复检查实际 CLI。
包含工程审查、用户角色模拟和行为验证，尚未进行陌生用户的真人可用性测试。

| 用户遇到的障碍 | 本轮改进 | 验证 |
| --- | --- | --- |
| 文档只构建程序，示例却直接调用 PATH 上的 molso | 补安装和直接运行方法 | release 构建；帮助实际调用 |
| 顶层帮助不显示路径选项；裸调用只说 missing command | 裸调用显示入门帮助，列出全局选项和起步步骤 | 首次调用、帮助主题测试 |
| 必须记住全局选项放子命令前，也不支持常见等号写法 | 使用 clap 统一解析；前后位置、等号写法都可用 | 自定义路径优先级和真实 exec 注入测试 |
| 未初始化或名称冲突时，先让用户输入，再报错 | 读取输入前检查存储及创建/更新条件；等待输入不持锁；提交时重新检查 | 保持 stdin 打开，确认错误不等待 EOF；并发写入回归 |
| 提示只说 credential，用户不知道正在填哪项 | 隐藏输入提示带凭据名称 | 真实 Unix PTY 检查提示、禁回显和 Enter 结束输入 |
| 错误只描述失败，用户或 agent 不知道下一步 | 增加 init、恢复原 key、list、update、PATH 或 stdin 等对应修复提示 | 初始化、更新、环境、启动失败回归 |
| 用户误把凭据放在 put 名称后，参数库会在错误中重复它 | put 多余参数只报告正确录入方式，不回显该参数 | 普通和以横线开头的虚构凭据测试 |
| exec 没有凭据映射时，仍因未初始化而无法执行 | 无映射时直接执行，不读 key/vault，不创建锁文件 | 未初始化时子进程执行、找不到命令的退出码测试 |
| 人工配置与 agent 调用混在一个流程里 | README 分成终端配置和 agent 消费；按消费方需要选择 env、stdin、管道 | 文档与实际帮助检查 |

## 产品判断与取舍

人负责初始化和录入，agent 只需要名称和消费方支持的接口。帮助及 README 先呈现
这条路径，存储格式与加密细节放在后面的说明中。GitHub 示例使用官方支持的
[GH_TOKEN](https://cli.github.com/manual/gh_help_environment)，不需要把凭据展开到 argv。

`exec --stdin` 需要消费方支持从 stdin 读取凭据，会占用它的整个 stdin。
需要其它业务输入的消费方应使用其支持的环境变量接口。首版没有为每个服务自动适配
命令；任意 CLI 并不都支持同一种凭据输入方式。

`get` 的非 TTY 检查无法区分正常消费管道和 agent 的日志收集管道。因此入门流程
优先展示 exec，并明确要求 get 与消费方位于同一次 shell 调用。没有更改原始字节
传递规则，也没有加入自动去换行、自动覆盖或读取后的确认步骤。

clap 代替手写解析器，引入了依赖成本，换来统一的帮助、错误用法提示及常见参数语法。
put 的多余参数诊断保留一个针对凭据的处理，避免重复可能误传的值；已经进入 argv
的值仍可能被外部进程或日志读取，不能靠这条诊断撤回。
`put` 在录入前额外读取一次 vault；提交仍重新检查，避免用户输入期间的并发变化
造成覆盖。首版小型本地 vault 接受这一开销，本轮没有做大规模性能测试。

后续需要真人观察首次录入和错误恢复，再决定是否增加状态检查命令、名称筛选和补全。
本轮没有为这些尚未观察到的需求增加配置层或交互流程。

## 用户模拟实测后的三项修正

2026-10-08，在 macOS 上用安装后的 CLI、隔离存储和虚构凭据走了 35 步用户流程。
初始化、隐藏录入、更新、取消、删除以及三种消费方式均可完成。消费方实际比较收到的
字节，只输出匹配结果。这个角色模拟不能代表陌生用户的学习时间，也不代表真实服务
认证或其它平台原生体验通过。

| 实际遇到的问题 | 修正行为 | 验证 |
| --- | --- | --- |
| 终端提示处只按 Enter，也成功存入空凭据，消费时才失败 | 隐藏输入为空时立即报错，既不创建也不替换；空流导入需要 `--stdin --allow-empty` | 真实 PTY 检查创建和更新失败后 vault 完全未变；原值仍可读取；空流导入回归 |
| `--udpate` 只得到笼统的录入方式错误 | 从 clap 的 SuggestedArg 保留已声明选项的建议，不回显未知参数或其它可能含输入的错误上下文 | 多种选项拼写错误、带误传虚构凭据的拼写错误及原有不回显测试 |
| 初始化后和全部删除后，空 list 没有可见反馈 | stdout 为终端时，在 stderr 给出“尚无凭据”和 put 下一步；管道和重定向保持静默 | PTY 分别检查 stdout/stderr；有项列表不提示；非终端空列表静默 |

这些修正沿用现有命令和输入路径，没有增加向导或配置项。原始字节不会自动去空格
或换行；空流必须明确允许。已同步到 put 帮助、README 和使用契约中。

## 发布前复查

进一步实测发现，生产凭据的进程失败且没有输出时，原先允许空流的 `put --stdin
--update` 会成功把旧值替换为空。因此默认拒绝空流，只有 `--stdin --allow-empty`
能明确保存空值。回归通过真实失败进程的 stdout 管道验证：新项不会创建，旧 vault
字节及旧凭据保持不变。这不会自动识别生产端已输出部分内容的失败，调用方仍需
检查生产端是否成功。

终端 init 输出增加 Key file / Vault 标签，脚本捕获时保留原来的两行路径；重复
初始化给出 list/put 下一步。exec 漏写 `--` 时给出明确的分隔符提示，原有子进程
参数透传契约继续保留。

README 的 GIF 从真实 PTY 进程输出录制并绘制为终端画面，使用临时存储和随机虚构
凭据；消费方只输出完整字节比较结果。生成脚本放在 `scripts/record-demo.py`，可在
macOS/Linux 用 Python 和 Pillow 重跑。
